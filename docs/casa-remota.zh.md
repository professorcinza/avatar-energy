# 基础 34 — 远程之家：团队基础设施

**Avatar-Energy · 基础 34 · 2026年8月22日**

*架构师决策（2026-08-22）：团队之开发管线运行于自托管、永远在线之远程 rakazo 实例。本基础先于基础设施规定设计——先过闸门，后花分文。*

---

## 问题

团队需与持久机器人 24/7 对话。替代方案——在架构师之机器上运行 stack——经三重验证而失败：(1) 机器会睡眠，例行程序不触发；(2) 将架构师之机器暴露于互联网，亦暴露其对 8 个仓库有 push 权限之 GitHub 凭据；(3) rakazo 处于 beta（生于 2026-08-13），托管产品"Rakazo Cloud"不存在——"随愿本地↔远程迁移"非该项目支持之操作。

答案为唯一之家，永远远程：机器人居于云端；架构师之机器为客户。

## INF 规格

| ID | 要求 | 源自 |
|---|---|---| 
| INF-001 | **唯一之家**：单一 rakazo 实例，永远远程且永远在线；无并行之本地团队实例——架构师之机器为客户（浏览器 + 本地 Hermes 用于直接终端工作） | 决策 |
| INF-002 | **诚实之尺寸**：VM 2 vCPU / 2–4 GB 内存 / ≥ 20 GB 磁盘（官方文档：2 GB 足够 API+worker+Postgres；本地 Docker 沙箱排除——E2B/Daytona 供应商承担机器人之计算机） | self-host.md |
| INF-003 | **沙箱在家外**：机器人计算机位于专用供应商（E2B 或 Daytona）——VM 只运行 API/worker/Postgres；执行隔离、可弃、绝不在应用 VM 上 | self-host.md |
| INF-003b | **模型凭据留于家中**：LLM 密钥以实例之 ENCRYPTION_KEY 加密存于 VM 之 Postgres；默认导出：**永不**——同 AVA-006 之法 | AVA-006 |
| INF-004 | **封闭注册**：`SIGNUP_ALLOWLIST` 限架构师之团队；无开放注册 | 决策 |
| INF-005 | **公共 HTTPS + 单一源**：WEB_ORIGIN/BETTER_AUTH_URL/API_URL 处于自有域名之 HTTPS 下；无明文 HTTP | self-host.md |
| INF-006 | **状态备份**：每日 Postgres 转储 + DATA_DIR（机器人 home、浏览器配置）保留 7 天；每季度测试恢复 | 运维 |
| INF-007 | **申报成本**：月度预算目标 ≤ US$ 20（Fly.io 2GB ≈ US$ 10.70；Hetzner CX22 4GB ≈ US$ 4.59 + 卷；E2B/Daytona 按用量）——偏差 > 20% 触发规格复审，而非沉默 | 决策 |
| INF-008 | **受控升级**：固定 rakazo 版本；升级仅于 changelog 审阅后——beta 期预计有破坏性变更 | self-host.md |
| INF-009 | **Hermes 不变**：本基础不改变架构师之本地 Hermes CLI——月度 D1 继续运行于 Hermes，直至等效例行程序存在于远程之家且经验证 | 决策 |
| INF-009b | **凭据离婚**：远程之家不继承架构师之 gh 会话——需要 GitHub 之机器人使用细粒度令牌（限于单一 fork 之 repo，或尽可能只读 deploy key），绝不用个人之 gho_ | 决策 |

## 设计

```
   团队（浏览器/手机，任意地点）
        │ HTTPS
        ▼
┌─────────────────────────────────────────┐
│ 家（永远在线 VM，Fly.io 或 Hetzner）    │
│  API ─ worker ─ Postgres ─ DATA_DIR     │
│  模型凭据：加密于此                     │
└────────────────┬────────────────────────┘
                 │ 沙箱供应商
                 ▼
┌─────────────────────────────────────────┐
│ 计算机（E2B/Daytona）                   │
│  每机器人 browser+shell，短暂存续       │
└─────────────────────────────────────────┘

架构师之机器 = 客户（浏览器）+ 本地 Hermes（自有终端）
```

## 本基础非什么

- 非通往"Rakazo Cloud"之桥（其不存在）；乃开源代码之自托管
- 不移动家之规格工作：规格继续诞生于仓库，三语，依 SDD
- 不取代架构师之 Hermes（INF-009）

## 角色

架构师决定供应商与域名，在家中配置模型凭据。双手执行：置备 VM、升起 stack（self-host 指南）、配置 allowlist、验证 HTTPS、测试备份。同一契约：草稿 → 审阅 → 验证。

## 验证（本规格如何自测）

| ID | 判据 |
|---|---|
| INF-001 | 供应商处仅列单一实例；无第二团队实例 |
| INF-002/003 | VM 上 `docker ps`/systemd 只见 API/worker/Postgres；计算机运行于沙箱供应商 |
| INF-005 | 公共源上 curl HTTPS：无 HTTP 降级；证书有效 |
| INF-006 | 于测试环境恢复之转储成为功能完整之实例 |
| INF-007 | 月账单 ≤ US$ 20 或有记录之复审 |
